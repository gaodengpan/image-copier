# Image-Copier 项目 Constitution

## 1. 代码质量与风格原则

### 1.1 Go 语言编码规范
**原则**: 所有 Go 代码必须符合 Go 社区最佳实践和官方编码规范。
- 必须使用 `gofmt` 格式化所有 Go 文件
- 遵循 Effective Go 指南中的建议
- 优先使用 Go 官方工具链进行代码检查

### 1.2 命名约定
**原则**: 包名、函数名、变量名应清晰表达其用途和含义。
- 包名应为简洁的小写单词，避免缩写
- 导出函数和类型使用 PascalCase
- 非导出函数和类型使用 camelCase
- 常量使用 UPPER_SNAKE_CASE

### 1.3 注释与文档标准
**原则**: 所有导出的函数、类型和包必须有清晰的注释和 Godoc 文档。
- 每个包必须有包注释说明其用途
- 每个导出函数必须说明其功能、参数和返回值
- 复杂算法或业务逻辑需要解释性注释

## 2. 测试策略原则

### 2.1 测试覆盖率
**原则**: 核心功能必须有充足的单元测试覆盖。
- 新增功能必须包含相应的测试
- 核心业务逻辑测试覆盖率不低于 80%
- 修复 bug 必须添加回归测试

### 2.2 测试类型与策略
**原则**: 采用多层次测试策略确保软件质量。
- 单元测试：验证独立函数和方法
- 集成测试：验证模块间协作
- 端到端测试：验证完整功能流程

### 2.3 测试命名规范
**原则**: 测试名称应清楚表达预期行为和测试场景。
- 使用 `Test<FunctionName>_<Scenario>` 格式
- 表格驱动测试中，子测试名称应描述具体场景

## 3. 错误处理策略原则

### 3.1 统一错误处理
**原则**: 项目内所有错误处理必须保持一致性。
- 在 internal/core/constants.go 中定义统一的错误消息
- 错误消息应包含足够的上下文信息
- 错误传播使用适当的错误包装

### 3.2 用户友好错误
**原则**: 向用户展示的错误信息必须清晰易懂。
- 避免显示技术性过强的内部错误
- 提供解决问题的具体建议
- 对敏感信息进行脱敏处理

## 4. 版本控制策略原则

### 4.1 分支管理
**原则**: 采用标准化的分支管理策略。
- 主分支（master）始终保持可发布状态
- 特性开发使用特性分支，命名格式 `feature/<descriptive-name>`
- 修复使用修复分支，命名格式 `fix/<descriptive-name>`

### 4.2 提交消息规范
**原则**: Git 提交消息必须清晰描述变更内容。
- 遵循约定式提交格式（feat:, fix:, refactor: 等）
- 提交消息应描述"什么"和"为什么"而非"如何"
- 保持提交原子性，单一提交只做一件事

### 4.3 版本发布
**原则**: 严格遵循语义化版本控制（SemVer）。
- 主版本号变化表示不兼容的 API 修改
- 次版本号变化表示向后兼容的功能添加
- 修订号变化表示向后兼容的错误修复

## 5. 依赖管理原则

### 5.1 第三方依赖引入
**原则**: 严格控制第三方依赖的引入。
- 评估依赖的安全性、活跃度和维护状态
- 优先选择官方库或广泛使用的成熟库
- 记录引入依赖的原因和风险评估

### 5.2 依赖更新策略
**原则**: 定期更新依赖以获取安全补丁和改进。
- 定期运行 `go list -u -m all` 检查更新
- 重要依赖的更新必须经过充分测试
- 记录依赖更新的影响评估

### 5.3 模块兼容性
**原则**: 维护模块接口的向后兼容性。
- 遵循 Go Module 的兼容性承诺
- 接口变更需提供迁移路径
- 在适当时候使用版本号标识重大变更

## 6. 安全考量原则

### 6.1 输入验证与防护
**原则**: 所有外部输入必须进行验证和净化。
- 在 internal/core/validation.go 中实现输入验证逻辑
- 防止命令注入和其他注入攻击
- 验证镜像名称和 URL 格式的合法性

### 6.2 凭证安全管理
**原则**: 敏感凭证必须安全存储和传输。
- 避免硬编码凭证到源代码中
- 使用环境变量或安全的配置文件管理凭证
- 访问外部服务时实施适当的认证和授权

### 6.3 安全审计
**原则**: 定期进行安全审计和漏洞扫描。
- 定期运行 `go list -m -u all` 检查已知漏洞
- 对依赖库进行安全扫描
- 建立漏洞响应和披露流程

## 7. TDD开发规范原则

### 7.1 TDD强制执行
**原则**: 所有代码变更必须遵循测试驱动开发（TDD）流程。
- **红阶段**: 首先编写验证功能需求的测试用例，此时测试应该失败
- **绿阶段**: 编写最少量的代码使测试通过
- **重构阶段**: 改进代码结构和设计，同时保持测试通过
- 修复 bug 或添加新功能前必须先编写相应的测试

### 7.2 TDD工具推荐
**原则**: 推荐使用 tdd-workflows:tdd-cycle 技能引导完整的TDD流程。
- 使用 `tdd-workflows:tdd-cycle` 技能来规范TDD周期的执行
- 此技能确保严格遵循红-绿-重构的开发循环
- 利用技能提供的框架来维持TDD纪律性和代码质量

### 7.3 测试质量标准
**原则**: 测试代码应与生产代码保持相同的标准。
- 测试代码应具备可读性、可维护性
- 确保测试具有确定性，不包含随机性或依赖外部状态
- 测试命名应清晰表达预期行为和测试场景

- 初始版本：v1.0.0
- 日期：2026-02-14
- TDD规范添加：v1.0.1

### 修订流程
- 任何对本 Constitution 的修改都需要通过核心维护者一致同意
- 重大修订需要进行公开讨论和意见收集

### 合规审查
- 每季度对本 Constitution 进行合规性审查
- 确保项目实践与 Constitution 原则保持一致
- 记录并处理任何偏离原则的情况

这份 Constitution 旨在为 image-copier 项目提供一致的开发和治理标准，确保项目长期健康可持续发展。
