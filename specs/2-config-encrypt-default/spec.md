# 配置加密提供者默认实现功能规格说明

## 1. 功能概述

### 1.1 功能名称
配置加密提供者默认实现（Config Encryption Provider Default Implementation）

### 1.2 功能描述
优化当前配置模块，将加密配置提供者（EncryptedViperConfigProvider）设为默认实现，使敏感信息（如账户密码、访问令牌等）在配置初始化和加载时自动加密存储和解密使用。新系统将在 config init 命令中加密敏感字段，并在 config load 时自动解密供 puller 使用。

### 1.3 背景
当前 image-copier 项目虽然已经实现了加密配置功能，但默认仍使用明文配置提供者。为了提高安全性和简化用户使用，需要将加密提供者设为默认实现，同时保持向后兼容性。

## 2. 用户场景与测试

### 2.1 主要用户场景
1. **配置初始化场景**：用户运行 config init 命令时
   - 用户输入敏感信息（如 GitHub Token、注册表用户名密码等）
   - 系统自动加密这些敏感信息并保存到配置文件
   - 明文不会以明文形式出现在配置文件中

2. **配置加载场景**：程序启动时加载加密配置
   - 应用启动时自动解密配置中的敏感信息
   - 解密后的信息用于正常业务流程
   - 用户无需手动解密即可正常使用功能

3. **向后兼容场景**：处理现有未加密配置
   - 旧版本明文配置仍然可以被正确加载
   - 系统平滑过渡到加密配置
   - 用户可以逐步迁移到加密配置

### 2.2 边界场景
1. **混合配置场景**：部分字段加密，部分字段未加密
2. **无效密钥场景**：使用错误的密钥尝试解密
3. **迁移场景**：从旧版未加密配置迁移到新版加密配置

## 3. 功能需求

### 3.1 默认加密实现需求
1. **REQ-DEFAULT-ENCRYPT**：系统默认使用 EncryptedViperConfigProvider 作为配置提供者
2. **REQ-AUTO-INIT**：在 config init 过程中，敏感字段应自动加密存储
3. **REQ-ENCRYPT-IDENTIFICATION**：加密值应带有 "encrypted:" 前缀以便识别
4. **REQ-NO-DOWNGRADE-SWITCH**：系统不允许用户通过配置开关降级到未加密模式，确保安全性

### 3.2 配置初始化加密需求
1. **REQ-INIT-ENCRYPT-GITHUB**：config init 中输入的 GitHub Token 必须加密存储
2. **REQ-INIT-ENCRYPT-REGISTRY**：config init 中输入的 Registry Username 和 Password 必须加密存储
3. **REQ-PLAINTEXT-INPUT**：用户可以在 config init 中输入明文，系统负责加密

### 3.3 配置加载解密需求
1. **REQ-LOAD-DECRYPT**：config load 命令应自动解密配置文件中的加密字段
2. **REQ-TRANSPARENT-DECRYPT**：解密过程对 puller 等消费者透明
3. **REQ-FIELD-EXCLUSION**：非敏感字段保持原样，不受加密解密影响

### 3.4 向后兼容需求
1. **REQ-LEGACY-SUPPORT**：系统应继续支持现有的未加密配置文件
2. **REQ-GRADUAL-MIGRATION**：支持逐步从明文配置迁移到加密配置
3. **REQ-COMPOSITE-FIELDS**：同时支持加密和未加密字段的配置文件

## 4. 非功能性需求

### 4.1 安全需求
1. **SEC-DEFAULT-ENCRYPTION**：默认配置路径必须提供加密保护 [硬性要求]
2. **SEC-AUTOMATED-PROTECTION**：用户不需要显式启用加密功能 [硬性要求]
3. **SEC-NO-DOWNGRADE**：系统不应降级到不安全的配置模式
4. **SEC-REALTIME-DECRYPTION**：系统应实时解密配置值而不缓存敏感信息，以最大化安全性

### 4.2 性能需求
1. **PERF-INIT-ENCRYPTION**：配置初始化时的加密操作不应显著增加执行时间
2. **PERF-LOAD-DECRYPTION**：配置加载时的解密操作应在合理时间内完成（<100ms）[硬性要求]
3. **PERF-COMPARISON**：加密配置的性能不应明显劣于纯明文配置

### 4.3 兼容性需求
1. **COMP-EXISTING-API**：现有的配置 API 和函数签名保持向后兼容
2. **COMP-ENV-VARS**：环境变量配置方式应继续有效，且能与加密配置协同工作
3. **COMP-FILE-FORMAT**：配置文件格式保持兼容，仅在敏感字段上应用加密
4. **COMP-FALLBACK-MODE**：在缺少加密密钥时系统应优雅降级到明文模式，但会显示安全警告

## 5. 成功标准

### 5.1 定量指标
1. **100%** 的新创建配置使用加密存储敏感字段
2. **> 95%** 的配置加载成功率（包括加密和未加密配置）
3. **< 150ms** 的平均配置加载时间（含解密处理）
4. **0** 个因加密配置导致的兼容性问题报告

### 5.2 定性指标
1. 用户能够无感知地使用加密配置功能而无需额外配置
2. 系统在新旧配置格式之间平滑切换
3. 安全审计确认所有敏感信息得到有效保护

## 6. 关键实体

### 6.1 加密配置提供者（EncryptedConfigProvider）
- 替代现有的 ViperConfigProvider 作为默认实现
- 处理加密配置文件的读取和解密
- 维护与现有配置 API 的兼容性
- 实现实时解密，不缓存敏感数据

### 6.2 配置初始化处理器（ConfigInitHandler）
- 在用户交互过程中自动加密敏感字段
- 将加密后的配置写入文件
- 提供清晰的加密状态反馈

### 6.3 向后兼容解码器（BackwardCompatibleDecoder）
- 识别并处理既有明文配置
- 透明处理混合配置（部分加密、部分明文）
- 提供平滑的迁移路径

### 6.4 默认配置工厂（DefaultConfigFactory）
- 统一创建默认配置提供者实例
- 确保系统始终使用加密提供者
- 管理配置提供者的生命周期

### 6.5 配置验证器（ConfigValidator）
- 在读取时验证加密字段的有效性和完整性
- 确保配置文件格式正确
- 提供详细的验证错误信息

## 7. 假设和约束

### 7.1 假设
1. 系统运行环境允许使用标准加密库
2. 用户可以接受通过环境变量（ENCRYPT_KEY）提供主密钥
3. 现有的配置验证逻辑适用于解密后的值
4. 在缺少加密密钥时，允许系统降级到明文模式是一种可接受的安全妥协

### 7.2 约束
1. 实现应尽量减少对现有代码库的影响
2. 解决方案应遵循 Go 生态的最佳安全实践
3. 必须保持与现有配置文件格式的兼容性
4. 不允许在内存中缓存解密后的敏感信息

## 8. 依赖关系

1. 依赖已实现的加密/解密功能（internal/encryption/ 包）
2. 与现有配置验证逻辑的集成
3. 与 CLI 命令（config init、config load）的集成

## Clarifications

### Session 2026-02-14

- Q: 是否必须将 EncryptedViperConfigProvider 设为绝对默认，还是可以保留选择机制？ → A: 必须设为默认实现，这是安全性要求
- Q: 对于向后兼容性，是否需要支持旧配置的自动加密升级？ → A: 优先支持读取，自动升级可以是未来增强功能
- Q: 性能指标是否为硬性要求？ → A: 保持当前阈值作为硬性要求
- Q: 需要加密哪些具体字段？ → A: GitHub Token、Registry Username、Registry Password 是必需加密的字段
- Q: 对于默认配置提供者的切换，是否需要提供一个配置开关让用户可以选择回退到未加密模式？ → A: 不提供开关，强制使用加密以保证安全，符合安全优先的设计理念
- Q: 如果环境变量ENCRYPT_KEY未设置，导致无法解密配置，程序应该如何处理？ → A: 在没有提供加密密钥时优雅降级到明文模式，但会显示安全警告
- Q: 如何处理现有的未加密配置文件的迁移？ → A: 保持向后兼容，同时支持明文和加密字段，但新写入的数据加密
- Q: 在应用程序运行期间，是否应该缓存解密后的敏感配置值以提高性能？ → A: 每次都需要实时解密，以最大化安全性，即使会影响性能
- Q: 何时应该验证加密配置字段的有效性和完整性？ → A: 在读取配置文件时验证加密字段的有效性
